# 盼之零商品卡证明修正

## 实机证据

扩展连续诊断确认，`.goods-list-with-game`、`.virtual-list`、`.empty`、`.all_game_list` 和 `.game-list` 都位于带 `aria-hidden="true"` 的 Element UI 游戏选择下拉框内。它们不是商品结果区，因此不能证明筛选结果为 0 条。

同一长驻 SPA 标签页还出现过“特战干员外观”字段缺失，说明复用页可能处于不完整状态，必须先恢复页面契约再采集。

0.3.0–0.3.1 实机快速任务进一步显示，盼之以可见文本“正在加载, 请稍后...”呈现页面级加载状态，但未提供 `aria-busy`、`role=status` 或稳定的 `.el-loading-*` 类。该可见加载文本必须优先于零商品卡证明处理。

## 最终行为

1. 正常任务仍直接复用已加载的唯一盼之目录标签，不承担约 32 秒的冷启动成本。
2. 第一次执行若返回 `missing_controls`，或筛选阶段返回 `operation_timeout`，后台只对该标签硬刷新一次，等待目录页加载完成后用新运行代号从筛选阶段重跑。
3. 第二次仍为可恢复失败时，仅在已有备用盼之标签的情况下切换一次；备用标签失败就结束任务。`structural_drift`、验证码、滑块和登录墙不会触发该重载或切换。
4. 0 条结果不再读取游戏下拉框类名。页面必须同时满足：
   - 文档加载完成；
   - 唯一可见“三角洲行动”标签存在；
   - QQ、可二次实名、两项指定特战干员外观、ALL 组合和价格输入控件全部可定位；
   - 全页没有任何 `/goodsDetails/` 链接，包括隐藏的旧链接；
   - 没有加载状态、网络/服务错误、验证码、滑块或登录墙；
   - 筛选动作完成后逐项验证选中状态与 `1900`–`4000` 价格；
   - 进入提交前和提交阶段各重新验证一次零商品卡状态。

## 现有标签回退

0.3.2 实机确认 Chrome 中存在两个相同目录 URL 的盼之标签，扩展固定选择最新标签；该标签硬刷新后仍缺少“特战干员外观”，另一个现有标签从未被尝试。0.4.0 增加有界回退：首选标签运行并硬刷新后仍返回可恢复失败时，排除当前标签，从其余现有盼之目录标签中按既有确定性排序选择一个，持久化新标签 ID，并且只再运行一次。该流程不创建、不关闭、不并行操作标签；候选为空或备用标签仍失败时立即结束任务。

0.5.0 实机确认页面默认不渲染“特战干员外观”，必须在“搜索筛条件”中检索后才出现；同一页还可能同时渲染两个筛选入口。扩展在等待完整页面契约前，按有界顺序清空其他入口并只激活一个入口，输入“特战干员外观”，随后把账号类型、实名、价格、皮肤选项和 ALL 语义的定位与校验限定在该入口对应的同一完整筛选面板内。

0.5.1 实机进一步确认刷新后的页面默认连“搜索筛条件”输入也不渲染，必须先点击唯一可见的“筛选不到？”入口。皮肤选项位于搜索弹层中，但组合方式位于弹层外的主筛选行；“全部都要有”还可能在展开当前组合方式前不进入 DOM。扩展现在先打开搜索界面，等待可见输入出现，再执行 0.5.0 的有界搜索；皮肤选项继续限定在当前搜索弹层，组合方式则只匹配同时包含字段名和两款目标皮肤的唯一可见主筛选行，并按需展开其组合方式下拉框。

实机还确认价格输入会让临时搜索弹层失效，因此动作顺序固定为：两款目标皮肤、组合方式、价格、账号类型、实名情况。后半段使用准备阶段已确认且仍连接在页面上的主筛选控件，避免为校验价格或基础选项而重新依赖已消失的搜索弹层。

页面可能同时渲染多个共享搜索状态的输入；设置其中一个会让另一个也显示“特战干员外观”。执行器因此保存本轮候选输入的节点引用，后续定位和证明显式携带该引用，而不是再按输入值重新选择搜索弹层。

该引用同时传入结果容器和加载状态读取。后台标签页在结果容器尚未挂载、仅显示“正在加载”时仍可被识别为有效加载态，并继续使用原有超时和稳定窗口等待。

0.5.1 的完整刷新实机还确认：无限滚动到达列表末尾时，页面不一定渲染结束标记，也可能完全不触发结果或加载 DOM 变动，而页面其他区域仍有动画噪声。采集器仅在受控滚动动作已经返回、完整观察窗口结束、结果签名始终一致且加载状态为否时，接受一次结果无增长；仍需连续两次独立观察才认定自然结束。结果以外的 DOM 变动不会作为完成证据，也不会提前结束观察窗口。

## 数据安全

快速刷新提交可信 0 条时保留已有完整基线。完整刷新仍经过现有骤降异常隔离，不能因单次 0 条直接清空历史数据。扩展仍不读取 Cookie、密码、localStorage、网络签名或页面脚本，也不会代替用户完成验证码、滑块或登录。
