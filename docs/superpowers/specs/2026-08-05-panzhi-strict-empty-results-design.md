# 盼之严格空结果设计

日期：2026-08-05

## 背景与证据

扩展 `0.2.0` 已在真实 Chrome 中领取新快速任务，正常复用了现有规范标签，但仍返回 `missing_controls`。安全遥测连续显示：筛选控件存在、页面可见且加载完成、没有商品详情链接，同时存在唯一的 `goods-list-with-game`、`virtual-list`、`virtual-list-phantom`、`virtual-list-container` 和 `empty` 类结构。失败发生在结果容器识别层，而不是领取、标签复用、心跳或租约层。

本地数据库当前保留 48 条可信盼之候选，并有已发布的完整结果血缘。公开商品搜索也没有证明当前存在同时满足两款目标外观、价格区间与可二次实名的在售账号。因此页面的零条结果是合理状态，但扩展必须严格证明空态，不能把任意缺卡页面当作成功。

## 已批准方案

### 严格识别空态

只有下列结构全部唯一、可见且属于同一分支时，才认定为盼之空结果：

- 一个 `.goods-list-with-game` 根；
- 根内一个 `.virtual-list`；
- 虚拟列表内各一个 `.virtual-list-phantom` 与 `.virtual-list-container`；
- 同一虚拟列表内一个可见 `.empty` 标记；
- 没有规范商品卡片，也没有加载指示。

缺少任一结构、出现多个候选、空标记不可见、仍在加载或存在冲突商品卡片时继续失败关闭。诊断只报告有限计数和类结构，不读取 Cookie、密码、localStorage、网络签名或页面脚本。

### 页面执行

`ResultState` 增加明确的 `emptyResultVisible`。空态具有稳定签名并被视为结果终点。筛选动作在“结果保持为空但控件已正确选中”时允许经过安静窗口完成，不要求凭空出现商品卡片。

严格核验价格、QQ、可二次实名、两个目标外观和 `ALL / 全部都要有` 后，如果结果仍为空，runner 不滚动，直接生成：

- `observedUniqueCount: 0`；
- `items: []`；
- `loadActionCount: 1`；
- `stopReason: "empty_result"`。

验证码、滑块或登录墙优先级高于空态；只要验证阻塞可见，就暂停并由用户处理，不生成空结果。

### 服务端安全契约

服务端只在 `stopReason === "empty_result"` 时接受零条快照，并要求计数、数组及加载次数与空态完全一致。所有其他结束原因仍至少需要一条合法商品和两次加载观察，不能借零数组绕过现有证明。

- 快速空结果：与完整基线合并，保留所有未观察到的旧盼之候选；当前 48 条不会被清空。
- 完整空结果：进入现有异常跌落保护；已有基线时隔离本轮，连续确认机制仍由仓库负责。没有基线时，严格空结果可以成为真实零条完整基线。
- 发布器继续原子写入扫描、来源状态、任务状态和调度状态。

### 协议与兼容性

`PanzhiPageSnapshot.stopReason` 增加 `empty_result`。后台严格解析器、服务端 Zod schema、发布器和文档同步更新。扩展版本升级为 `0.2.1`，方便 Chrome 扩展页确认加载的是本次构建。

## 测试与验收

自动化测试必须证明：

- 精确唯一空态可识别；普通空容器、重复虚拟列表、隐藏空标记和加载态均拒绝；
- 筛选后保持空结果时 runner 完成零快照且不执行滚动；
- 验证阻塞仍优先于空态；
- 后台只接受严格零快照组合；
- 服务端拒绝伪造零结果，快速零结果保留完整基线，完整零结果触发现有隔离；
- 非空快照、标签复用、运行代号、租约恢复和验证码回归不变。

实机验收重新加载 `0.2.1` 后先执行快速任务，要求任务成功并保留候选；再验证完整空结果不清空、验证码自动暂停/继续，以及 Service Worker 重启恢复。
