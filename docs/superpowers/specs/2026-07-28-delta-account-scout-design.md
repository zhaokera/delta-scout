# 三角洲账号候选台设计说明

## 目标

在本机运行一个 Web 应用，聚合交易猫、盼之代售和螃蟹账号中公开可见的《三角洲行动》QQ 官服账号信息，自动淘汰不符合条件的商品，并用可解释的评分帮助用户挑选后再回到原平台交易。

本期固定硬条件：

- 登录端：QQ 官服。
- M7 皮肤：`棱镜攻势`，且品质必须是 `极品`。
- 价格：不高于 ¥6,000。

“优品”、未提及品质、描述矛盾或无法核验的 M7 商品均不进入推荐候选。用户关注的角色红皮、M7 品质和巨浪会被独立展示。

## 范围与边界

应用只读取各平台在正常访问中公开展示的商品列表和详情页；不绕过验证码、登录墙、频率限制或反爬机制，不保存账号密码、Cookie、实名资料或付款资料。

首次扫描优先使用无需登录的公开目录页。如某个平台在访问时要求登录或验证码，来源卡片显示“需要人工处理”，保留原始链接并暂停该来源；用户可以在 Codex 浏览器中自行完成正常登录或验证后通知助手继续。登录、验证码和最终下单付款始终由用户完成。

本工具只给出候选和原始来源链接，不承诺账号可交易、可换绑、不会被找回或不会因游戏规则被处理。

## 交互设计

首页为“候选账号台”。顶部固定展示当前的三项硬条件和“更新候选”按钮；来源状态区分别显示交易猫、盼之和螃蟹账号的最近更新时间、条目数或阻塞原因。

候选表按推荐分排序，包含来源、价格、总资产、实名/包赔标签、红皮数量、巨浪状态、推荐分和数据置信度。默认只显示通过全部硬条件的账号。用户可改变排序、展开筛选，或仅查看“待人工核验”条目。

选择一行后，详情面板显示：

- M7 `棱镜攻势` 的原文证据、解析品质和核验状态；
- 角色红皮的名称列表及数量；
- 巨浪的持有状态、品质（原页面明确时）和原文证据；
- 总资产、哈夫币及其他能可靠解析的资产；
- QQ 官服、实名状态、二次实名、包赔、验号时间、封禁相关说明；
- 评分原因、最近抓取时间、原始描述和“在原平台查看”链接。

所有没有足够证据的字段显示“待人工核验”，而不是补全或猜测。

## 数据来源与采集流程

每个平台都有一个隔离的来源适配器：`jiaoyimao`、`panzhi` 和 `pxb7`（螃蟹账号）。适配器只负责：定位《三角洲行动》目录、读取公开商品摘要、访问少量商品详情、输出原始证据和标准化前字段。页面结构变化、访问受阻和解析失败限制在单个平台内，不影响其他来源。

更新动作按以下顺序执行：

1. 读取每个平台已知的公开入口，采用保守并发与请求间隔。
2. 采集摘要后，以价格、QQ 官服和标题/摘要中的 M7 线索预筛。
3. 仅对可能命中的商品抓取详情页；保存原始文本摘录、URL 和抓取时间。
4. 标准化字段、应用硬筛选、去重并计算评分。
5. 把结果写进本地 SQLite，前端刷新来源状态和候选表。

商品的唯一键为 `source + platform_listing_id`；当站点未公开稳定编号时，以规范化 URL 作为退化键。绝不跨平台把不同商品自动合并：相似账号只以“可能重复”提示，仍各自保留来源链接。

## 标准化模型

`Listing` 记录至少包含：

- `source`、`sourceListingId`、`url`、`title`、`capturedAt`、`evidence`；
- `priceCny`、`loginPlatform`、`service`、`totalAssetsM`、`hafCoins`；
- `m7PrismStatus`：`absent`、`unknown`、`premium`、`peak`、`conflicting`；
- `redSkins`：已命名角色红皮数组，另存 `redSkinCount`；
- `julangStatus`：`unknown`、`absent`、`owned`，及可选 `julangQuality`；
- `realNameStatus`、`secondRealNameAvailable`、`recoveryCoverage`、`verificationAt`；
- `parseWarnings` 和 `confidence`。

文本解析以明确词组和可追溯证据为准：`棱镜攻势` 与 `极品` 必须同时出现才映射为 `peak`；出现 `优品` 映射为 `premium` 并被硬筛掉。角色红皮和巨浪也仅从明确的名称/品质描述或结构化字段中提取。

## 过滤与排序

硬筛选依次检查：QQ 官服、价格可解析且不高于 6000、M7 状态为 `peak`。任何未知或冲突值均不进入默认候选列表，但可在“待人工核验”中查看。

通过硬筛选后，推荐分由下列部分组成，并在详情中逐项解释：

- 账号安全信息：40 分（可二次实名、包赔、近期验号、明确风险提示）。
- 价格合理性：25 分（同批候选的价格与资产比较，不把低价本身当作安全）。
- 可核验资产：20 分（总资产、哈夫币和可靠的高价值物品）。
- 收藏亮点与数据置信度：15 分（已命名角色红皮、巨浪信息和证据完整度）。

分数不是估值或安全承诺；缺失资料会降低置信度，并将原因公开显示。

## 技术方案

采用 TypeScript 本地项目：React + Vite 渲染候选台，Express 提供本地 API 与采集任务，SQLite 保存快照和来源状态，Cheerio 解析获取到的 HTML。采集器使用标准 HTTP 请求，带来源级限速、超时、重试上限和明确的 User-Agent；不会模拟绕过受保护页面的行为。

前端只同本机 API 通信。后端以适配器接口注入来源实现，解析器和评分引擎保持为纯函数，便于使用 HTML 夹具进行确定性测试。配置文件保存来源入口、采集上限和评分权重，不保存平台凭据。

## 失败处理

- 某来源访问失败：保留该来源最近成功快照，标记陈旧与失败原因；其余来源继续运行。
- 页面结构变化或字段无法解析：保存受限长度的原文证据和解析警告，条目进入人工核验，不进入默认推荐。
- 达到页面/详情上限：停止本轮该来源，显示“部分更新”，不无限请求。
- 本地数据库不可写：本轮不覆盖旧快照，向界面返回可操作错误。

## 验收与测试

自动化测试使用三个来源的离线 HTML 夹具，覆盖：价格和资产解析、M7 优品/极品/缺失/冲突识别、红皮与巨浪提取、硬筛选、评分可解释性、去重键、来源失败隔离和 API 响应。集成测试使用假适配器，绝不在测试中访问交易平台。

手动验收时，在 Codex 浏览器打开本地候选台，确认固定条件、三平台状态、候选表与详情证据可见；在各来源公开页面存在可访问商品时，核对至少一条商品的价格、M7 品质、红皮/巨浪字段和原始链接一致。若来源要求登录或验证码，应当显示人工处理状态而不尝试规避。
