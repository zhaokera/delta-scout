# 盼之 Chrome 自动刷新设计

## 目标

在现有候选台刷新中心内，把盼之从“定时提醒用户执行浏览器快照”改为“定时任务自动驱动用户现有 Chrome 中的一个盼之标签页”。快速刷新和每日完整刷新都不需要用户手工点击、筛选、滚动或提交；只有登录失效、验证码或滑块验证出现时才通知用户接管。用户完成验证后，自动流程继续执行。

本设计只解决盼之刷新自动化，不改变候选准入、评分、排序、快照异常保护或其它平台的刷新逻辑。

## 已确认事实

- 现有 `RefreshScheduler` 在盼之到期时只写入 `attention_required`，不会启动采集。
- 现有盼之浏览器快照接口已经校验原生筛选证明、可见商品、价格范围、快速增量合并和完整快照发布。
- 盼之公开目录 HTML 响应很快，但只包含未按目标条件筛选的首批 SSR 商品。
- 盼之筛选分页接口在没有浏览器签名时返回阿里云 WAF HTML；客户端还把该接口列为需要动态 WASM 签名的接口。因此服务端直接调用不是稳定方案。
- 用户手工打开盼之页面速度正常，所以自动化应复用现有 Chrome 会话，不以 Codex 应用内浏览器的加载时间作为性能依据。

## 用户体验

### 一次性设置

用户只需把仓库中的 `extensions/panzhi-auto-refresh/` 作为“已解压的扩展程序”加载一次，并授权访问：

- `https://www.pzds.com/*`
- `http://127.0.0.1:4310/*`

扩展还需要 `alarms`、`tabs`、`scripting`、`storage` 和 `notifications` 权限，分别用于定时领取、复用标签页、执行可见页面操作、恢复任务和提示人工验证；不申请浏览历史、下载、剪贴板或全站访问权限。

扩展复用用户当前 Chrome 的盼之登录态。它不读取、导出或保存 Cookie、密码、验证码、localStorage 或网络签名。

刷新中心的现有盼之卡片显示扩展连接状态。扩展后台每 60 秒向本机发送一次空闲心跳；两分钟内收到过心跳才显示“Chrome 自动刷新已连接”。未连接时给出固定的安装目录和简短安装说明，但不新增顶级菜单。

### 日常运行

1. 本地 API 进程继续作为刷新计划的唯一权威来源。
2. 盼之快速或完整刷新到期后，调度器把该轮标记为等待浏览器自动执行，并保留刷新模式。
3. Chrome 扩展通过低频本机轮询发现待执行轮次。若存在多个盼之目录标签页，先选规范 URL 完全匹配的标签页，再选同目录路径的标签页；同级候选取 `lastAccessed` 最新者，仍并列时取最小 tab ID。扩展不关闭用户已有的其它标签页。只有完全没有匹配标签页时才新建一个。
4. 扩展在页面上应用价格 `1900–4000`、可二次实名、两款指定红皮和 `ALL / 全部都要有`，随后验证页面可见状态与服务端要求的筛选证明一致。
5. 快速模式最多执行 6 次加载并收集最多 60 张卡片；完整模式滚动到连续两次无新增，并遵守现有 100 次加载、500 张卡片保护上限。
6. 扩展把现有严格快照格式提交给本机接口。服务端继续负责解析、增量合并、异常隔离、原子发布和下一次计划更新时间。
7. 成功后标签页可以留在后台供下一轮复用；不创建多个盼之标签页。

候选台不增加新的顶级菜单。现有刷新中心的盼之卡片改为展示自动执行阶段，并保留“立即快速刷新”和“立即完整刷新”按钮。这两个按钮只是提前排队，后续步骤仍由扩展完成。

## 架构

### 本地服务端

服务端保留现有 `refresh_schedule` 作为持久化计划，并新增独立的 `panzhi_browser_jobs` 表保存自动执行任务。计划与任务各自职责如下：

- `refresh_schedule` 只决定何时应有一轮 `quick` 或 `deep`；
- `panzhi_browser_jobs` 保存任务标识、模式、状态、租约、令牌摘要、验证期限、通知时间、错误和最终发布结果；
- 数据库最多允许一个盼之非终态任务，唯一约束在事务内阻止重复入队。

盼之到期或用户点击立即刷新时：

- 在事务内创建任务或与已有非终态任务合并；
- 不通过公共采集协调器读取未筛选 SSR 数据；
- 向扩展提供只监听 `127.0.0.1` 的当前任务查询接口；
- 接收扩展的阶段、等待验证和失败状态；
- 通过与现有 `/api/sources/panzhi/browser-snapshot` 相同的内部发布服务校验并发布快照。

重复触发遵循以下确定规则：

- 没有非终态任务时创建新任务；
- 已有 `quick` 任务且尚未进入 `collecting` 时，新的 `deep` 触发把同一任务原子升级为 `deep`；
- 已有任务处于 `collecting`、`awaiting_user_verification` 或 `submitting` 时，不改变正在运行的模式；新的 `deep` 触发只在 `refresh_schedule` 中保留为仍然到期，当前任务终态后立即创建下一轮 `deep`；
- 同模式或更低优先级的重复触发合并到现有任务，并返回同一任务标识；
- 入队和失败不推进 `next_quick_at` 或 `next_deep_at`。只有可信快照发布成功才按完成时间推进相应计划；失败使用现有退避规则，待执行的 `deep` 不会被一次 `quick` 成功清除。

任务领取必须具备租约和幂等语义。同一轮只能被一个扩展执行；服务工作进程或 Chrome 重启后，未完成任务可再次领取并从安全阶段重做。

### 自动任务接口契约

新增接口统一使用 `/api/sources/panzhi/automation` 前缀：

- `GET /status`：返回扩展连接状态和当前任务的公开阶段，不返回执行令牌；
- `POST /heartbeat`：记录扩展空闲心跳；
- `POST /jobs/claim`：原子领取或续领当前任务，返回任务模式、租约截止时间和随机执行令牌；
- `POST /jobs/:id/heartbeat`：验证 Bearer 令牌并续租；
- `POST /jobs/:id/state`：验证令牌后更新允许的阶段、验证等待或失败信息；
- `POST /jobs/:id/snapshot`：验证令牌和 `PanzhiBrowserSnapshotSchema` 后发布任务快照；
- `POST /jobs/:id/cancel`：取消当前任务。

现有 `/api/sources/panzhi/browser-snapshot` 保留给人工诊断和兼容用途。扩展必须使用带任务认证的新 snapshot 路径；新路径调用同一个内部快照发布服务，避免复制校验与合并逻辑。

令牌只出现在 `Authorization: Bearer <token>` 请求头中，数据库只保存摘要。快照发布、扫描历史、变化事件、任务 `success` 和刷新计划推进必须在同一个数据库事务中完成。成功请求的响应结果和规范请求体摘要保存在任务行中；成功后该令牌不能再续租、改状态、取消或提交不同快照。仅当同一任务以同一 Bearer 摘要重放完全相同的规范请求体时，snapshot 路径把它识别为非授权性的幂等响应重放，返回 `200`、相同发布结果和 `deduplicated: true`，不得创建第二轮扫描历史或重复变化事件。错误令牌返回 `401`，不存在或已过期任务返回 `404`，其它终态任务提交返回 `409`。

### Chrome 扩展

扩展使用 Manifest V3，由以下部分组成：

- 后台 service worker：使用 `chrome.alarms` 低频查询本机任务、维护单任务互斥、寻找或创建唯一盼之标签页、转发阶段与快照；
- 盼之 content script：只操作页面可见控件、识别验证状态、读取可见商品卡片并执行有节奏的滚动；
- 小型纯函数模块：负责筛选状态验证、商品卡片归一化、验证码/登录墙识别，供自动化测试复用。

扩展不复制盼之签名算法，不重放请求，也不从开发者工具或浏览器存储读取认证材料。它只使用用户在正常页面中本来就能执行的可见操作。

### 通信与权限

扩展后台使用 Chrome 的 `host_permissions` 访问本机 API 和盼之页面。所有本机接口继续绑定 `127.0.0.1`，请求体使用严格 schema 和大小限制。

扩展领取任务时获得仅对该轮有效的随机执行令牌；令牌不出现在候选台日志、URL 或通知中。阶段更新和最终快照必须同时携带任务标识和令牌。任务成功、取消、重新领取或过期后旧令牌立即失去任务控制权；成功任务仅保留上节限定的同体 snapshot 响应重放能力。

## 状态流

盼之自动任务使用以下用户可见状态：

1. `queued`：等待 Chrome 扩展领取；
2. `opening_page`：正在复用或打开盼之标签页；
3. `applying_filters`：正在设置并核对原生筛选；
4. `collecting`：正在读取快速窗口或完整结果；
5. `awaiting_user_verification`：检测到登录墙、验证码或滑块，暂停并通知用户；
6. `submitting`：正在向本机接口提交严格快照；
7. `success`：可信快照已发布；
8. `failed`：结构变化、超时或不可恢复错误，旧快照继续可用；
9. `cancelled`：用户取消本轮，旧快照继续可用。

所有状态都带最后更新时间。正常租约为 2 分钟，扩展执行期间每 30 秒心跳一次，每次续租 2 分钟。`awaiting_user_verification` 仍遵循相同心跳和续租规则，不永久锁定所有权；同时任务保存独立的 24 小时 `verification_deadline_at`。

租约到期后，服务器使旧令牌失效并把同一任务恢复为 `queued`。新领取者必须从 `opening_page` 开始，重新应用和核对全部筛选条件。服务器通过持久化的 `verification_notified_at` 保证同一段连续验证阻塞在 24 小时内只弹一次通知；验证消失并恢复采集后清除该去重标记。这样既不会并发执行，也不会因 Chrome 关闭几分钟而永久卡住任务。

扩展把当前 `jobId`、令牌、模式和被选中的标签页 ID 保存到 `chrome.storage.local`。Chrome 或 service worker 重启后先尝试心跳恢复原租约；租约已失效则删除旧令牌并重新领取同一服务端任务。标签页 ID 失效时重新执行确定性的标签页选择。已采集的卡片只保存在内存，重启时明确丢弃并从 `opening_page` 重做，不提交不完整缓存。

## 验证码与人工接管

检测到验证码、滑块或登录墙时，扩展必须：

- 立即停止点击、输入和滚动；
- 把任务标记为 `awaiting_user_verification`；
- 聚焦现有盼之标签页并发送一次 Chrome 通知；
- 不读取或填写账号、密码、短信码和验证码；
- 等待页面验证元素消失且目录页重新可用后，重新核对全部筛选条件，再从安全阶段继续。

验证码或登录墙中断时不提交部分快照。等待期间不自动重复刷新页面，不并发创建新标签页，也不反复弹通知。用户完成验证后，扩展从 `applying_filters` 重新开始；超过 24 小时仍未处理则本轮以 `captcha_required` 失败、保留旧快照并按现有退避策略重新安排。

## 失败处理与数据安全

- 页面结构变化：失败关闭，不提交猜测数据，并保留上一份可信快照。
- 本地 API 暂时不可用：扩展指数退避，不改变盼之页面状态；API 恢复后继续领取。
- 提交时与其它刷新冲突：保留已收集快照，在有限次数和带抖动的退避后重试提交。
- 快速刷新没有完整基线：自动升级本轮为完整模式，而不是要求用户手工处理。
- 快速窗口未出现的商品：继续由现有合并逻辑保留，不判定下架。
- 完整刷新数量异常：继续使用现有异常隔离规则，不覆盖可信基线。
- Chrome 未运行或扩展未安装：任务保持排队并在候选台明确显示，不伪装成刷新成功。

## 性能与节奏

- 扩展空闲时最多每 30–60 秒查询一次本机任务，不访问盼之。
- 页面操作等待可观察的 DOM 变化，不使用高速固定点击循环。
- 快速刷新以现有 6 次加载、60 张卡片为上限，目标是在页面正常时数分钟内完成。
- 完整刷新每天一次，串行滚动；任何验证码出现都立即暂停。
- 同一时刻只允许一个盼之自动任务，并继续服从应用的全局快照提交锁。

## 测试与验收

### 自动化测试

- 调度器：盼之到期产生可领取任务，不再只产生无人执行的提醒。
- 任务仓库：quick/deep 合并或升级、唯一非终态任务、领取租约、心跳、过期恢复、令牌校验和重复提交幂等。
- 接口：查询、领取、阶段更新、验证码等待、取消和成功提交的状态码及严格校验。
- 扩展后台：多个既有标签页时确定性选择一个、不关闭其它标签页；没有时只创建一个；并发闹钟不会重复执行。
- 页面脚本：从固定 HTML fixture 中定位筛选控件、证明 ALL 语义、提取唯一卡片、识别验证码和登录墙。
- 快速/完整模式：分别验证加载上限、无新增停止条件和中断恢复。
- 重启恢复：有效租约续领、失效令牌重新领取、失效标签页重新选择，并明确丢弃内存中的不完整卡片。
- 发布事务：扫描历史、变化事件、任务成功和计划推进同时成功或同时回滚；重复 snapshot 返回相同结果。
- 回归：现有盼之快照、三平台互斥、异常保护、候选保留和其它平台刷新测试继续通过。

### 实机验收

在用户现有 Chrome 中完成以下验证：

1. 扩展安装后，连续两次快速刷新无需手工点击或滚动；
2. 两轮都只使用同一个盼之标签页；
3. 提交结果包含 `1900–4000`、可二次实名和双红皮 ALL 的严格筛选证明；
4. 人为停在验证码页面时自动操作停止、只通知一次；
5. 用户完成验证后自动恢复并成功发布；
6. 关闭 Chrome、重启 Chrome 和重启本地 API 后，排队任务均能恢复；
7. 任一失败场景都不清空或覆盖上一份可信快照。

只有上述实机验收通过后，刷新中心才把盼之标为“自动刷新已启用”。

## 不在本次范围

- 绕过、破解或自动完成盼之验证码、滑块和 WAF；
- 读取或导出浏览器 Cookie、密码、token、localStorage 或网络签名；
- 直接调用需要动态签名的盼之筛选 API；
- 修改交易猫或螃蟹的采集策略；
- 新增独立顶级菜单或同时打开多个盼之标签页。
