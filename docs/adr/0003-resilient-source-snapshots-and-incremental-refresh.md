# ADR-0003: 保留可信来源快照并区分快速增量覆盖

## Status

Accepted

## Context

三个平台的刷新能力并不对称：交易猫和盼之可能需要登录浏览器处理
验证，螃蟹则能通过公开列表接口稳定分页。此前只要某来源本轮受阻，
候选读取层就会把该来源从统一评分中移除，即使数据库仍保存着最近一次
成功快照；同时螃蟹每 30 分钟的“快速刷新”仍扫描约 70 页，与每日完整
刷新没有实质区别。

这会造成两个问题：短暂验证失败会让 Top30 的平台构成突然失真；高频
全量扫描浪费时间和平台请求预算。界面此前只显示页数、商品数和完成
状态，也无法解释采集方式、平台原生筛选证明，以及“平台返回到 Top30”
之间的数据损耗。

## Decision

1. 来源本轮受阻或失败时，只要存在最近一次成功快照，就继续对该快照
   统一评分并允许进入候选池。来源状态仍保持 `blocked`/`failed`，
   `lastSuccessAt` 不更新，界面明确标记为“沿用可信快照”，不得冒充本轮
   新数据。
2. 螃蟹快速刷新只扫描公开原生筛选结果的前 6 页。新观测商品按稳定 key
   覆盖旧商品，窗口外商品原样保留；快速刷新不据此判定下架，也不把未
   观测商品的稳定轮次加一。
3. 螃蟹每日完整刷新继续扫描到平台自然末页。只有完整刷新可以把未再次
   出现的商品记录为下架，并作为异常量保护和完整覆盖的基线。
4. 增量轮次同时记录“本轮平台返回数”和“合并后可信快照数”。
   `quick_window` 不与完整页数基线比较，避免因主动缩小窗口触发数据骤降
   隔离。
5. 来源状态接口返回采集方式、筛选证明说明、原生筛选标签、快照状态和
   最近观测数量。PC 界面展示“平台返回 → 本地合格 → Top30”漏斗，并在
   总览中报告当前最新来源覆盖数。
6. 盼之浏览器快速快照沿用同一增量语义：服务端验证原生筛选证明，合并
   上次可信快照，并单独记录可见卡片数；浏览器登录信息、Cookie 和平台
   签名不进入应用数据库。

## Consequences

### Positive

- 平台短暂验证失败不会再让可信候选瞬间从 Top30 消失；
- 来源新鲜度与排名可用性被拆开表达，用户能判断哪些账号需要再次验号；
- 螃蟹快刷从约 70 页降为最多 6 页，仍由每日完整刷新校正下架和长尾变化；
- 三个平台的筛选条件和漏斗数量可以在同一界面审计。

### Negative

- 沿用快照中的商品可能已经下架，购买前仍必须打开平台详情复核；
- 螃蟹快刷窗口外的价格或描述变化最多延迟到每日完整刷新；
- 来源状态与扫描历史需要同时区分观测数量和发布快照数量，数据模型更复杂。

### Neutral

- 评分公式和平台公平规则不变；新鲜度只作为可见标记，不给任何平台加分；
- 人工淘汰仍优先于快照保留，被淘汰账号不会因后续合并重新进入 Top30。

## Alternatives Considered

**受阻来源继续退出候选池**

- 未采用：把采集可用性误当成账号质量，会造成平台席位和排名非业务性跳变。

**螃蟹每次都完整扫描**

- 未采用：数据最完整但高频重复读取长尾页面，刷新耗时与请求量过高。

**快刷未出现即判定下架**

- 未采用：快速窗口只覆盖头部，无法对窗口外商品做负面判断。

**根据快照新鲜度调整评分**

- 未采用：会重新引入平台能力差异造成的隐性加减分。界面标记和购买前复核
  足以表达时效风险。
