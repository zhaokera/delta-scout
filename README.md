# 三角洲账号候选台

本地运行的《三角洲行动》账号比较工具。它读取交易猫、盼之代售和螃蟹账号的公开商品页面，并用同一套规则评估账号。入池硬条件为：

- QQ 官服
- 明确可二次实名
- 价格在 ¥1,900–¥4,000（含边界）
- 同时拥有骇爪-维什戴尔和露娜-黑天际线

M7「棱镜攻势」不再硬性入池，只作为可筛选的品质标签和低权重价值项；没有 M7、优品 A/B/C、品质未知或证据冲突都不会单独淘汰账号。候选台同时展示角色红皮、M7 品质、巨浪、总资产、哈夫币、资产回收率、实名状态、包赔信息、原文证据、解析置信度、扫描稳定性和可解释推荐分。推荐分拆成“账号价值”“购买安全”和“数据完整度”，并把已发现风险与安全证据不足分开表达。待核验的 M7 或巨浪不会伪装成“明确没有”，页面会在确定推荐分之外显示潜力上限。详情还会展示可信价格轨迹、关键字段变化和当前在售状态。默认候选池兼顾三个平台，也可以切换为完全按分数排序的跨平台总榜；可从列表勾选最多 4 个账号，在横向决策矩阵中比较价格、分数、皮肤资产和安全证据。

## 启动

环境要求：Node.js 24+、pnpm。

```bash
pnpm install
pnpm dev
```

随后在浏览器打开：

```text
http://127.0.0.1:4311/
```

前端开发服务运行在 `4311`，本地 API 运行在 `4310`。刷新是异步任务，页面会持续显示阶段和进度，不需要让一次 HTTP 请求保持打开。

### 盼之 Chrome 自动刷新（一次性安装）

先运行 `pnpm build:panzhi-extension`，再在 Chrome 打开 `chrome://extensions`、开启“开发者模式”、点击“加载已解压的扩展程序”，选择 `extensions/panzhi-auto-refresh/dist/`。保持 `pnpm dev` 运行并进入 `http://127.0.0.1:4311/refresh` 刷新中心后，盼之卡片会显示“Chrome 自动刷新已连接”，定时和立即刷新都会由扩展自动执行；若遇到登录、滑块或验证码，Chrome 会聚焦原标签页并等待你处理，完成后自动继续。详细安装、恢复与安全边界见 [盼之 Chrome 自动刷新扩展说明](extensions/panzhi-auto-refresh/README.md)。

## 三种刷新方式

| 操作 | 覆盖范围 | 使用场景 | 登录与验证 |
| --- | --- | --- | --- |
| 刷新公开数据 | 交易猫、盼之代售、螃蟹账号三个平台 | 通过服务端限速读取无需登录的公开入口；一次完整刷新结束后统一发布 | 不使用浏览器登录态；交易猫若出现 CAPTCHA 会标记阻塞 |
| 刷新交易猫 | 仅重新采集交易猫，保留盼之和螃蟹的正式快照 | 公开入口被验证阻塞时，由当前 Codex 任务通过浏览器辅助采集 | 必须在同一个 Codex 浏览器标签页由用户亲自登录或完成 CAPTCHA；Codex 只读取页面可见商品 |
| 盼之自动刷新 | 仅重新采集盼之，保留交易猫和螃蟹的正式快照 | Chrome 扩展默认只读取最新窗口并与上一份完整快照合并；每天一次再滚动到无新增 | 登录、滑块或验证码由用户亲自处理，完成后自动继续；只读取可见商品卡片 |

三种刷新互斥；已有任务运行时，另一个入口会显示冲突并继续展示正在运行任务的进度，不会清空候选。多个候选台标签页会同步交易猫任务，成功发布后再统一重载来源、候选、扫描历史和已打开账号的历史。单平台浏览器刷新只替换对应平台正式商品，但会保留另两个平台并对三个平台重新评分和生成候选池。交易猫快速刷新会复用商品 ID、标题和卡片原文完全一致且没有解析警告的详情；Top30 边缘与待核验账号按本地抓取时间使用 6 小时窗口，其余稳定账号使用 24 小时窗口，每天的完整刷新仍强制重新核验。二次实名未知或任何可见文本变化时仍会重新核验，页面展示的验号时间与包赔状态缺失不会再导致无意义的重复请求；达到详情预算后 5 分钟自动补扫。本轮价格始终使用新列表值。完整操作见 [交易猫 Codex 浏览器刷新操作手册](docs/jiaoyimao-browser-refresh-runbook.md) 和 [盼之原生价格筛选快照操作手册](docs/panzhi-browser-snapshot-runbook.md)。

## 自动刷新与变化提醒

服务端使用 SQLite 保存各平台的刷新计划，即使候选台页面关闭，应用进程仍会继续调度；应用退出期间不会在后台运行，重新启动后会从持久化计划继续。默认安排如下：

| 平台 | 快速刷新 | 每日完整刷新 | 特殊处理 |
| --- | --- | --- | --- |
| 交易猫 | 每 60 分钟 | 每 24 小时 | 验证码后退避 2 小时，不自动绕过验证 |
| 盼之 | 每 120 分钟自动快刷 | 每 24 小时自动完整刷新 | Chrome 扩展自动执行；登录、滑块或验证码出现时暂停并等待用户 |
| 螃蟹 | 每 30 分钟扫描最新 6 页并合并 | 每 24 小时扫描到自然末页 | 公开分页串行采集，页间隔 600 ms；只有完整刷新判定下架 |

所有计划加入 ±10% 时间抖动并共用全局刷新锁，手工刷新、定时刷新和浏览器任务不会同时写入正式快照。限流按 30 分钟起指数退避、最长 6 小时；普通失败按 5、15、60、120 分钟逐级退避。交易猫快速刷新继续读取完整列表并复用可信详情：高分候选最多复用 6 小时，其他稳定商品最多复用 24 小时；完整刷新不复用协调器详情缓存。盼之与螃蟹的快速刷新只更新顶部最新窗口并合并到上一份完整快照，未出现在窗口内的商品不会被判定为下架；每日完整刷新负责校正长尾变化。

快照发布后会记录并展示值得复核的变化：新进入全局 Top10、单次降价至少 ¥100、资产回收率提升至少 10 个百分点、新发现 M7 珠光/炫彩/糖果材质、下架或不再满足筛选、安全信息变化。事件可在候选台标记为已读，历史保留在本地数据库中。设计取舍见 [分层刷新与 SQLite 持久化调度 ADR](docs/adr/0001-layered-refresh-scheduler.md)。

交易猫浏览器任务的首次创建响应会显示一次性接管码。当前状态查询永远不会再次返回该码；如果刷新页面后丢失且 Codex 尚未接管，请取消该任务并重新创建。取消只终止本轮采集，已有候选和旧快照继续可用。

### 交易猫浏览器任务状态

| 状态 | 页面含义 | 处理方式 |
| --- | --- | --- |
| `awaiting_codex` | 等待 Codex 接管 | 把本次一次性接管码交给当前 Codex 任务 |
| `collecting_list` | 正在采集列表 | 按服务端节奏读取可见商品卡片 |
| `collecting_details` | 正在核验详情 | 只核验价格未知或位于 ¥1,900–¥4,000 的必要详情 |
| `awaiting_user_verification` | 等待人工验证 | 用户在同一标签页完成登录或 CAPTCHA |
| `cooling_down` | 限流冷却中 | 等待服务端给出的时间，禁止主动重试 |
| `validating` | 正在校验完整性 | 服务端检查自然末页、筛选和详情覆盖 |
| `committing` | 正在提交可信快照 | 原子写入中，不要重复发起任务 |
| `success` | 刷新完成 | 交易猫快照已发布，三平台已重新评分 |
| `quarantined` | 新结果已隔离 | 本轮结果未发布，继续使用旧可信快照 |
| `paused` | 任务已暂停 | 验证、结构变化或进程恢复后等待继续 |
| `failed` | 刷新失败 | 不覆盖旧快照，可检查原因后重新创建 |
| `cancelled` | 已取消 | 本轮停止，已有候选不受影响 |
| `expired` | 任务已过期 | 创建或“继续等待”后的 24 小时窗口已结束 |

任务、采集游标和暂存证据写入本地 SQLite。应用重启后，未处于提交阶段的活动任务会恢复为 `paused` 并保留原阶段和游标；同一个仍持有闭包客户端的 Codex 任务可以在 24 小时窗口内继续。未接管任务仍可用原一次性码接管；已经丢失的一次性码不会从 API 恢复。“我还在处理，继续等待”会从操作时刻重新延长 24 小时。`committing` 中断会安全标记失败，避免半发布；超过期限则清除活动凭据并进入 `expired`。

## 人工淘汰与恢复

打开一个合格账号的详情后，可以点击“人工淘汰”，选择固定原因并填写补充说明。“其他”必须填写说明，其余原因的说明可选，最多 500 字。保存成功后：

- 该账号立即退出平台均衡候选、全局 Top 30 和“全部合格”，下一名会按现有评分自然补位；
- 账号进入“已淘汰”，列表和详情会显示原因，详情还会显示说明和处理时间；
- 同一台电脑打开的其它候选台标签页会自动刷新该决定；
- 刷新采集、重启软件、商品暂时下架后以同一稳定编号重新出现，都不会清除决定。

人工决定只作用于这一个平台商品编号，不会自动扩散到疑似重复账号或其它平台。点击“恢复参与排名”后，账号重新按原有硬条件和评分参与候选；恢复不保证一定进入 Top 30。

淘汰和恢复会以追加事件保存在本地 SQLite，历史原因不会被覆盖。这些反馈会以保守、可解释的方式辅助后续排名：与“价格虚高、M7 不值、红皮不合适、安全风险、资产不足”淘汰号特征相近的账号，每命中一条有效反馈下调 1 分；同一原因最多 4 分，累计最多 8 分。调整会在列表和详情显示“人工偏好”标签，只改变推荐总分与顺序，不改变硬条件、基础价值、安全得分或风险等级。恢复淘汰后，对应影响立即消失。“卖家问题”和“其他”因缺少可靠的卖家标识或结构化语义，只排除原商品，不会错误扩散到整个平台。

## 三平台状态

| 平台 | 当前公开采集方式 | 受限时的处理 |
| --- | --- | --- |
| 交易猫 | 目录 HTML 只用于验证页面结构；随后 MTop 查询从第 1 页开始使用页面原生 `1900,4000`、可二次实名条件，并通过“干员外观多选”同时要求“骇爪-维什戴尔”和“露娜-黑·天际线” | 遇到 CAPTCHA 时标记“验证码阻塞”，可由用户登录后的 Codex 浏览器继续 |
| 盼之代售 | 由用户 Chrome 中安装的扩展使用页面原生最低价 `1900`、最高价 `4000`、可二次实名，并在“特战干员外观”以 `ALL / 全部都要有` 同时选择两款指定红皮；快速模式最多加载 6 次并与完整快照合并 | 用户自行处理登录和验证；扩展不读取 Cookie，平台置顶的越界或缺项商品不会进入候选 |
| 螃蟹账号 | 公开 JSON 查询同时携带原生价格项 `[1900,4000]`、可二次实名和“干员皮肤”全部满足条件，要求“骇爪维什戴尔”与“露娜黑天际线”；保留服务端 `pageToken` 并递增 `pageIndex`，直到空列表或游标消失 | 接口或字段结构变化时保留旧快照并标记来源异常 |

平台页面会变化。三个平台都先使用各自原生价格、可二次实名与双指定红皮 AND/ALL 筛选，不预选 M7，再由本地规则做第二次校验。交易猫的 MTop 从第 1 页开始，`searchCondition` 包含 `1900,4000`、可二次实名及平台公开的“干员外观多选”条件；盼之使用浏览器中可见的两个价格输入框、可二次实名、“特战干员外观”两项及 `ALL / 全部都要有` 模式；螃蟹使用公开页面定义的价格项、可二次实名项，以及“干员皮肤”属性 `1037114` 的两个公开物品 ID，并以 `filterType: 1`、`isAll: true` 表达“全部满足”。任何平台返回的置顶或异常商品仍由本地统一复核：明确不可二次实名直接淘汰，状态未知进入待人工核验，只有明确可二次实名才能进入合格池和 Top 30。

## 数据与分类规则

- 完整刷新时，交易猫和螃蟹会在原生 1900–4000 价格筛选下持续读取到平台自然末页；两者各自最多 650 页、10,100 条唯一摘要，螃蟹最多接收 10,100 个内嵌详情。螃蟹快速刷新最多读取前 6 页，把新观测按商品 key 合并到完整快照，单独记录“本轮返回数”和“可信快照数”，不产生窗口外下架记录。交易猫默认综合排序下优先核验前 120 个详情，达到详情预算后仍继续扫描全部列表；后续商品只有在列表卡已经同时证明 QQ 官服和实名状态时才参与候选评分，否则进入待人工核验。交易猫允许最多连续 3 个全重复分页，避免动态排序造成的单页抖动过早截断。盼之快速增量最多 6 次加载、60 张卡片，按商品 ID 覆盖并保留上一份完整快照；每天的完整刷新仍以连续两次无新增为结束，接口最多接受 500 个唯一可见卡片并再次丢弃区间外商品。盼之自动模式遇到验证码会暂停且不提交部分快照；只有诊断用人工端点可将 `captcha_required` 快照记录为 `partial`。
- 螃蟹每页最多 16 条；服务端 `pageToken` 可能跨页保持不变，因此分页同时依赖递增的 `pageIndex`，不能把重复游标误判为结束。响应中的 `total` 不作为总数证明，只有空列表或游标消失才是自然末页。平台均衡候选池每个平台最多展示 10 条；“全局 Top 30”不设平台配额。两个推荐池只排除明确高风险账号；跨平台疑似同号仍会显示参考提示，但每条平台商品都独立参与排名，不会因为疑似重复而被候选池剔除。
- 三个平台在一次刷新中并行采集；每个平台内部仍保持串行分页，交易猫与盼之同一来源请求间隔至少 2 秒，螃蟹公开分页至少 600 ms，单次请求 15 秒超时并最多重试一次。
- 商品必须同时证明 QQ、官服、可二次实名、价格在 ¥1,900–¥4,000（含边界），并精确证明拥有骇爪-维什戴尔和露娜-黑天际线，才进入“合格候选”；任一硬条件未知或只证明其中一款红皮则进入“待人工核验”，明确不可二次实名或缺少任一指定红皮则淘汰。
- M7 的“棱镜攻势”、成色（极品或优品）和品质等级必须来自同一条证据记录，禁止跨字段拼接。
- M7 品质 S/A/B/C、角色红皮、巨浪、总资产和哈夫币会进入详情与评分；备注中与 M7 同一语境的珠光、炫彩、糖果（糖果纸）会标为高价值模板。M7 只是品质标签和价值项，不能替代 QQ 官服、可二次实名、¥1,900–¥4,000 与双指定红皮硬条件。
- M7 极品、优品、未发现、品质未知或证据冲突都按同一准入规则处理；低于 ¥1,900、高于 ¥4,000、微信、明确非官服或不可二次实名会因为硬条件进入“已淘汰”。M7 信息不完整会降低该标签的得分或数据完整度，但不会单独把账号送入待核验。
- 用户人工淘汰的合格账号也会进入“已淘汰”，并从两个候选池和“全部合格”移除；恢复后再按原评分重新参与。
- 候选列表 API 只传输价格、评分、皮肤资产、安全状态等决策摘要；原始描述、证据正文和完整评分解释在打开单个账号时按需读取，避免完整视图重复传输数 MB 文本。详情读取失败时仍保留摘要并明确提示，不把摘要当作完整核验结果。
- 基础推荐分按 `账号价值 × 80% + 购买安全 × 10% + 数据完整度 × 10%` 直接计算为 100 分；最终推荐分为 `基础推荐分 + 人工偏好调整`，偏好调整只会扣分且最多扣 8 分。账号价值的 100 分分配为：M7 15、已识别付费红皮 25、巨浪 15、价格与性价比 20、资产 25。露娜-黑·天际线与骇爪-维什戴尔各按 ¥300 估值，其他已识别红皮各按 ¥250 估值，每 ¥50 折算 1 个红皮价值分并封顶 25 分；同一款皮肤只计一次，同一角色拥有多款已明确命名红皮时可分别计价。资产按 `1M ≈ ¥2` 折算，500M 达到资产项 25 分上限；价格与性价比拆成价格位置 10 分和资产回收率 10 分，其中价格位置固定按任务价格带 `¥1,900–¥4,000` 线性计算，不随某个平台本轮采集量变化，资产估值达到报价的 60% 时拿满回收率分。M7 珠光/炫彩/糖果模板在 M7 的 15 分上限内最多增加 3 分且不叠加。购买安全只计入“可二次实名”10 分，同时仍作为入池硬门槛；验号时间和永久包赔仅保留为人工参考标识，不增加安全分、推荐分或排名权重。
- 未知计分字段不直接进入确定分；M7 或巨浪仍待核验时，页面额外显示假设其成立后的“待核验潜力”上限，并只在确定分完全相同时用于温和排序。推荐分内部保留一位小数，减少大量整数并列。只有二次实名状态未知时才标记为“安全证据不足”；明确不可二次实名或存在封禁备注时为高风险。验号时间与永久包赔仅作参考，不能改变风险等级、安全分或推荐分。
- 每轮扫描会记录来源结果和商品物质指纹，本地只保留最近 50 轮。只有来源连续两轮都完整扫描成功、且账号物质字段不变时才标记“连续稳定”；首次出现、发生变化或任一轮来源不完整会分别标记为首次、变化或待观测。
- 每次被接受的完整扫描都会保存结构化可信观察，包括价格、M7/红皮/巨浪、资产、安全字段、置信度和解析提示。详情接口 `GET /api/listings/:key/history?limit=20` 返回最近观察、字段变化以及 `active/removed/unknown` 在售状态；只有可信完整扫描才能生成下架记录。
- 若完整扫描的商品数低于可信基线一半且至少减少 10 条，或页数低于一半且至少减少 2 页，系统会隔离第一次低量结果并继续使用上次可信快照。只有下一次完整扫描落在相近低量区间才确认发布；恢复正常会自动清除保护。`partial`、验证码阻塞和失败轮次不能确认低量结果，也不能把缺失账号误记为下架。
- 刷新 API 异步返回。`success` 会发布新快照；`partial` 会发布本轮可用来源并明确展示异常来源；`failed` 不覆盖现有快照。某来源受阻或失败时，最近一次成功的可信快照继续参与统一评分和候选池，但来源卡会标为“沿用可信快照”、保持旧的成功时间，并显示当前观测为 0，避免把旧数据冒充为本轮结果。前端在刷新或进度查询失败时也不会清空当前候选与已选详情。
- 单条详情异常会把该来源标为 `partial`。若一开始就连续 3 条详情受阻或失败，立即停止该来源并保留旧快照；若本轮已经成功核验至少 20 条详情，则连续 3 条受阻会打开详情熔断、停止后续详情请求但继续完成公开列表分页，保留已取得的新鲜数据并按 `partial` 发布。两种情况都不会误记为完整成功，也不会继续请求加重平台风控。
- 超过 24 小时未成功更新的来源会显示为陈旧。

本地快照、人工淘汰/恢复事件、最近 50 轮扫描历史和稳定性观察保存在 `data/scout.sqlite`，该目录已从 Git 排除。应用启动时会按当前解析、准入、去重和评分规则重新计算已有商品；不会改写人工淘汰记录、扫描历史或可信观察。

## 安全边界

- “刷新公开数据”只读取无需登录即可访问的公开商品信息；交易猫辅助刷新只在同一 Codex 浏览器标签页读取可见内容，盼之自动刷新只在用户 Chrome 中由扩展选定的一个标签页读取可见筛选与商品内容。
- 用户必须亲自完成登录和 CAPTCHA。Codex 不查看输入内容，不代填、不绕过验证，也绝不导出 Cookie、localStorage、sessionStorage、密码、验证码答案或认证请求头。
- 一次性接管码、bridge token 和 action permit 只在当前任务内短暂使用；数据库只保存不可逆哈希，不把原值写入日志、文档、页面证据或客户端状态查询。
- 螃蟹公开响应中的 `pageToken` 只在单次刷新内存中作为分页游标，刷新结束即丢弃，不写入 SQLite、日志、证据或配置。
- 软件和 Codex 不代替用户处理或绕过 CAPTCHA，不逆向未公开接口。
- 三个平台保持串行、限速的只读采集；遇到 CAPTCHA、页面结构变化或公开接口异常时记录为 blocked/partial/failed，不尝试规避平台限制。
- 不自动下单、不联系卖家、不代替用户登录或付款。
- 页面中的解析结果仅用于缩小候选范围。购买前必须回到原平台重新验号，重点确认 M7 品质、区服、二次实名、找回包赔、封禁记录及商品是否仍在售。
