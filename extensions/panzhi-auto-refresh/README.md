# 盼之 Chrome 自动刷新扩展

这个 Manifest V3 扩展连接本机候选台 API，自动领取盼之快速或完整刷新任务。它只操作 `www.pzds.com` 页面可见控件和商品卡片，复用一个确定的标签页；不会读取 Cookie、密码、验证码答案、localStorage、网络签名或页面脚本，也不会绕过平台验证。

## 一次性安装

1. 在项目目录运行：

   ```bash
   pnpm install
   pnpm build:panzhi-extension
   pnpm dev
   ```

2. 在 Chrome 地址栏打开 `chrome://extensions`。
3. 打开右上角“开发者模式”。
4. 点击“加载已解压的扩展程序”，选择项目里的 `extensions/panzhi-auto-refresh/dist/`。如果误选了父目录 `extensions/panzhi-auto-refresh/`，构建后也能正常运行，避免出现“看似安装成功但后台未启动”。
5. 打开 `http://127.0.0.1:4311/refresh` 进入刷新中心。盼之刷新卡片通常会在 30 秒内显示“Chrome 自动刷新已连接”。

扩展源码或清单更新后，重新运行 `pnpm build:panzhi-extension`，再到扩展页点击该扩展的“重新加载”。构建目录只包含 `manifest.json`、`background.js` 和 `content.js`，由构建命令重建，不提交到 Git。

## 日常使用

保持 `pnpm dev` 和 Chrome 运行即可。定时任务会自动排队；也可以在现有盼之卡片点击“立即快速刷新”或“立即完整刷新”。扩展会直接复用已经加载完成的盼之目录标签页，不会在正常任务开始时重载它；没有合适标签时才新建一个。如果复用页缺少任一必需筛选控件，或筛选阶段卡在加载中，扩展会自动硬刷新该标签并只重试一次。重试仍失败且 Chrome 已经存在另一个合适的盼之标签时，扩展会切换到排序最优的现有标签再尝试一次；不会新建、关闭或并行操作多个标签。仍不完整才安全失败，避免人工刷新和无限重载。随后扩展设置并严格核对以下条件，再采集页面可见商品：

- 价格 `1900`–`4000`；
- “可二次实名”；
- “特战干员外观”选择“骇爪-维什戴尔”和“露娜-黑天际线”；
- 组合方式为 `ALL / 全部都要有`。

快速刷新最多执行 6 次加载并接收 60 张卡片；完整刷新最多接收 500 张卡片，并在连续两次没有新增后结束。滚动到底且结果签名在完整观察窗口内保持不变、期间未出现加载状态时，会记为一次无增长；必须连续确认两次才结束，页面其他区域的动画或计时器不会被当作结果完成证据。旧可信快照会一直保留到新快照完成校验和原子发布。

筛选完成后，扩展只有在文档已完整加载、目标游戏和全部必需筛选控件都可见、筛选值已逐项核验、全页不存在任何规范或隐藏的 `/goodsDetails/` 商品链接、没有加载状态、网络错误、登录、滑块或验证码时，才会认定为可信的 0 条结果；提交前还会再次核验。该证明不依赖盼之游戏选择下拉框的内部类名。快速刷新遇到可信 0 条时保留完整旧基线；完整刷新遇到骤降为 0 条时继续经过异常隔离，不会直接清空历史商品。

遇到登录、滑块或验证码时，扩展会立即停止自动步骤、聚焦原标签页并发出通知。请只在页面里亲自完成验证，不要关闭该标签页；阻塞消失后，扩展会自动回到筛选阶段继续。连续阻塞只通知一次，不会循环打扰。

## 断线与恢复

候选台显示“Chrome 自动刷新未连接”时，按顺序检查：

1. 确认本机 API 正常：

   ```bash
   curl -fsS http://127.0.0.1:4310/api/health
   curl -fsS http://127.0.0.1:4310/api/sources/panzhi/automation/status
   ```

2. 确认 Chrome 扩展已启用，加载的目录是 `extensions/panzhi-auto-refresh/dist/`，目录内存在三个构建文件。
3. 若刚更新代码，重新构建并在 `chrome://extensions` 点击“重新加载”；错误按钮可查看服务工作线程的启动错误。
4. 等待最多 30 秒。扩展心跳两分钟未到达时，页面才会判定为断开。

API 重启后，未完成任务保存在 SQLite 中；Chrome 会重新领取它。Chrome 或扩展 Service Worker 重启后，扩展会恢复保存的任务标识和原标签页选择；非验证状态会硬刷新一次再从头采集，验证码、滑块或登录状态则保留原页面等待用户。每次页面执行都有唯一运行代号，恢复后的新执行会让遗留执行停止，避免两个 runner 同时点击。若等待验证时原标签页被关闭，扩展只会复用另一个已经打开的盼之目录标签；没有合适标签时本轮安全失败并由调度器退避重排，不会悄悄在别处继续。

当前协议版本对应扩展 `0.5.1`。重新构建并加载后，可在 `chrome://extensions` 的扩展卡片上用版本号确认是否已经生效。

`0.5.0` 会在页面默认未展示“特战干员外观”时，自动使用“搜索筛条件”展开该字段。若页面同时渲染多个筛选入口，扩展只激活一个入口，并把全部筛选、校验和采集绑定在同一筛选面板内。

`0.5.1` 会在搜索输入尚未渲染时先自动点击唯一可见的“筛选不到？”，等待搜索界面出现后再继续上述流程。皮肤选项严格绑定当前搜索弹层；组合方式则精确绑定同时包含字段名和两款目标皮肤的唯一可见主筛选行。若“全部都要有”采用延迟渲染，会先展开该主筛选行的组合方式下拉框。

如果页面的多个搜索输入共享同一状态，扩展会记住本轮实际尝试的输入节点，后续皮肤选择、组合方式和证明全部沿用该节点对应的搜索弹层，不会因为其他输入同步出相同文字而切换面板。

同一输入引用也会贯穿结果加载观察，因此后台标签页暂时只有“正在加载”且结果容器尚未挂载时会继续有界等待，不会因为同步搜索输入产生结构歧义而提前失败。

由于价格等主筛选动作可能关闭临时搜索弹层，`0.5.1` 会先完成两款皮肤和组合方式，再使用已确认的主页面控件设置价格、账号类型和实名情况。

完整刷新到达无限滚动列表末尾时，页面可能既不显示“没有更多”，也不产生加载节点或结果 DOM 变更，同时页面其他区域仍有动画噪声。`0.5.1` 会等待完整超时窗口后，把“结果状态零变动且零加载”的滚动记为一次无增长，并用第二次独立观察确认；无关 DOM 变动不会提前完成观察窗口。

## 诊断兜底

`POST /api/sources/panzhi/browser-snapshot` 仍保留给页面结构测试和人工诊断。正常自动刷新不要直接调用它，也不需要手写快照。诊断步骤与严格证明格式见 [盼之原生筛选快照操作手册](../../docs/panzhi-browser-snapshot-runbook.md)。
